# Job Hunting U — RAG Chatbot Backend

A retrieval-augmented chatbot API that answers website visitor questions
from Job Hunting U's internal documents and, when it can't help, points
visitors to the Contact Us page for a discovery call. Retrieval runs
locally (ChromaDB + sentence-transformers); answers are generated by
Gemini (`gemini-flash-lite-latest`).

The chat UI itself lives in the main site's React app
(`frontend/src/components/ChatWidget.jsx`), not in this folder — this
service is API-only. Lead capture (name/email/phone/message) happens on
the existing Contact Us page, which writes to the SQL database (source
of truth) and syncs to Systeme.io from `backend/server.js`. (Syncing
leads to Airtable as well is a deferred follow-up task, not yet wired up.)

```
chatbot-backend/
├── main.py            # FastAPI server (/api/chatbot/chat, /api/chatbot/health)
├── ingest.py          # Document indexer
├── rag.py             # RAG pipeline with Gemini
├── requirements.txt
├── Dockerfile
└── .env.example
```

## 1. Setup

```bash
cd chatbot-backend
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Copy the env template and fill in your credentials:

```bash
cp .env.example .env
```

You need a Gemini API key in `.env`:

- **`GEMINI_API_KEY`** — get one at https://aistudio.google.com/apikey

`.env` is never committed and no credential is ever hardcoded — every
module that needs one loads it via `python-dotenv`.

By default the indexer reads documents from `./knowledge_base_jhu`
(relative to this folder). Change `KNOWLEDGE_BASE_DIR` in `.env` if your
documents live elsewhere.

## 2. Build the knowledge base

Run this once, and again any time the `.docx` files change:

```bash
python ingest.py
```

This reads all documents — including any Word **tables** (e.g. the
pricing tiers table), not just paragraph text — splits them into
400-word chunks (50-word overlap), tags each chunk with its source
filename and detected section (from Word Heading 1/2 styles), embeds
them with the local `all-MiniLM-L6-v2` model, and stores everything in
a persistent ChromaDB collection at `./jhu_vectordb`. Progress prints
per file as it runs.

Note: `docker build` runs this automatically at image build time (see
`Dockerfile`), so the vector DB is always in sync with whatever
`knowledge_base_jhu/` contains at build time — no manual step needed
for a container deploy.

## 3. Start the server

```bash
uvicorn main:app --reload --port 8000
```

Check it's healthy:

```bash
curl http://localhost:8000/api/chatbot/health
```

Test a query:

```bash
curl -X POST http://localhost:8000/api/chatbot/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "How much does Job Hunting U cost?", "history": []}'
```

## 4. Run with Docker

```bash
docker build -t jhu-chatbot-backend .
docker run --env-file .env -p 8000:8000 jhu-chatbot-backend
```

Or via the repo's root `docker-compose.yml`, which already wires this
service up behind Traefik at `/api/chatbot/*` on the production domain.

## 5. Update the knowledge base later

Whenever the source documents change:

1. Edit the `.docx` files in `knowledge_base_jhu/`.
2. Re-run `python ingest.py` from this folder — it fully rebuilds the
   `jhu_knowledge` collection, so stale/removed content never lingers.
3. Restart (or rebuild/redeploy) the server so it picks up the
   refreshed `jhu_vectordb/` data.

No code changes are needed for routine content updates.

## Notes

- The chatbot **only** answers from retrieved document context — if the
  answer isn't in the knowledge base, it responds with a warm handoff
  and points the visitor to the Contact Us page instead of guessing.
- Every response includes `sources`: the document filenames the answer
  was grounded in. The frontend never renders these to visitors — they're
  logged server-side per query for debugging/QA only.
- Conversation history (last 6 messages) is sent with every request so
  Gemini has short-term context, and is kept entirely in the browser —
  no server-side session storage.
- The bot will describe client-facing outcomes (e.g. "we automatically
  send your onboarding materials") but is explicitly instructed never
  to name internal tools, software, or vendors — even if they appear in
  the source documents — so internal-only operational details never
  leak to a website visitor.
- There is no lead-capture endpoint in this service. All lead capture
  happens on the Contact Us page (`/contact`), which is the single
  source of truth (SQL) and syncs to Systeme.io. Syncing leads to
  Airtable as well is a deferred follow-up, not yet implemented.
