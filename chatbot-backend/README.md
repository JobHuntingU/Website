# Job Hunting U — RAG Chatbot

A retrieval-augmented chatbot that answers website visitor questions from
Job Hunting U's internal documents and encourages them to book a discovery
call. Retrieval runs locally (ChromaDB + sentence-transformers); answers
are generated by Gemini (`gemini-flash-lite-latest`). Visitors who show
interest can submit their name, email, phone, and resume directly in the
widget — leads are stored in Airtable and Jerry gets emailed automatically.

```
jhu_chatbot/
├── backend/
│   ├── main.py            # FastAPI server (/chat, /leads, /health)
│   ├── ingest.py          # Document indexer
│   ├── rag.py             # RAG pipeline with Gemini
│   ├── airtable_client.py # Lead storage (Airtable API)
│   ├── requirements.txt
│   └── .env.example
├── frontend/
│   └── widget.html        # Embeddable chat widget + lead capture form
└── README.md
```

## 1. Setup

```bash
cd jhu_chatbot/backend
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Copy the env template and fill in your credentials:

```bash
cp .env.example .env
```

You need two sets of credentials in `.env`:

- **`GEMINI_API_KEY`** — get one at https://aistudio.google.com/apikey
- **`AIRTABLE_API_KEY`**, **`AIRTABLE_BASE_ID`**, **`AIRTABLE_TABLE_NAME`** —
  for lead storage. Create a Personal Access Token at
  https://airtable.com/create/tokens scoped to your leads base with
  `data.records:read` and `data.records:write`. The base needs a table
  (default name `Leads`) with these exact fields: `Name` (single line
  text), `Email` (email), `Phone` (phone number), `Questions Asked`
  (long text), `Client_Resume` (attachment).

`.env` is never committed and no credential is ever hardcoded — every
module that needs one loads it via `python-dotenv`.

By default the indexer reads documents from `../knowledge_base_jhu`
(relative to `backend/`), i.e.:

```
JHU-Chatbot/
├── knowledge_base_jhu/
│   ├── 01 - Business Plan.docx
│   ├── 02 - Product Ecosystem & Pricing.docx
│   ├── 03 - Onboarding & Recruitment Framework.docx
│   ├── 04 - Lead Generation & Sales.docx
│   ├── 05 - The Job Hunting Methodology.docx
│   ├── 06 - 2026 AI Tool Guide.docx
│   └── 07 - Internal Operations & Automations.docx
└── jhu_chatbot/
    └── backend/
```

Change `KNOWLEDGE_BASE_DIR` in `.env` if your documents live elsewhere.

## 2. Build the knowledge base

Run this once, and again any time the `.docx` files change:

```bash
python ingest.py
```

This reads all 7 documents — including any Word **tables** (e.g. the
pricing tiers table), not just paragraph text — splits them into
400-word chunks (50-word overlap), tags each chunk with its source
filename and detected section (from Word Heading 1/2 styles), embeds
them with the local `all-MiniLM-L6-v2` model, and stores everything in
a persistent ChromaDB collection at `./jhu_vectordb`. Progress prints
per file as it runs.

## 3. Start the server

```bash
uvicorn main:app --reload --port 8000
```

Check it's healthy:

```bash
curl http://localhost:8000/health
```

Test a query:

```bash
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "How much does Job Hunting U cost?", "history": []}'
```

## 4. Embed the widget on any website

Open `frontend/widget.html` and update two constants near the top of
the `<script>` block:

- `API_URL` — point this at your deployed backend
- `CALENDLY_URL` — Jerry's Calendly (or similar) link; shown to a lead
  right after they submit the form so they can pick a call time
  immediately. Leave blank to just show a confirmation message instead.

Then paste the entire file's contents (the `<div>`, `<style>`, and
`<script>` blocks) just before `</body>` on any page:

```html
<!-- paste the contents of widget.html here, right before </body> -->
```

That's the whole integration — no build step, no dependencies, no
iframe. The widget renders a floating "Chat with us" bubble in the
bottom-right corner.

## 5. Lead capture

Every widget has a **"Book a Call"** button in the header, and an
inline **"Yes, let's talk →"** button automatically appears under any
bot reply that mentions a discovery call. Both open a form (name,
email, phone required; resume optional, PDF/DOC/DOCX up to 5MB) that
POSTs to `/leads`.

On submit, the backend:

1. Creates a record in your Airtable `Leads` table via
   `airtable_client.py`
2. Uploads the resume (if provided) as an attachment on that record
3. Returns success/failure to the widget, which shows a confirmation
   screen (with the Calendly link, if `CALENDLY_URL` is set)

To get notified by email whenever a lead comes in, set up an **Airtable
Automation** (no code needed): in the base, go to **Automations** →
**Create automation** → trigger **"When a record is created"** (table:
`Leads`) → action **"Send email"** → build the message using Airtable's
field-insert picker so it includes the real Name/Email/Phone/Questions
Asked/Client_Resume values, not static text. Test it, then flip the
automation to **ON**.

## 6. Deploy to Railway

1. Push this repo (or just the `jhu_chatbot/backend` folder) to GitHub.
2. In Railway, create a new project → **Deploy from GitHub repo**.
3. Set the root directory to `jhu_chatbot/backend` (if deploying the
   whole monorepo).
4. Add environment variables in Railway's dashboard (mirror `.env`):
   - `GEMINI_API_KEY`
   - `GEMINI_MODEL` (optional, defaults to `gemini-flash-lite-latest`)
   - `CHROMA_DB_PATH` (optional, defaults to `./jhu_vectordb`)
   - `CHROMA_COLLECTION_NAME` (optional, defaults to `jhu_knowledge`)
   - `AIRTABLE_API_KEY`, `AIRTABLE_BASE_ID`, `AIRTABLE_TABLE_NAME`
5. Set the start command:
   ```bash
   uvicorn main:app --host 0.0.0.0 --port $PORT
   ```
6. **Important:** `jhu_vectordb/` is built locally by `ingest.py` and is
   not regenerated automatically on deploy. Either:
   - commit the `jhu_vectordb/` folder to the repo so it deploys as-is, or
   - run `python ingest.py` in a Railway shell / one-off deploy step
     after the source `.docx` files are available on the server.
7. Once deployed, copy the Railway public URL into `API_URL` at the top
   of `widget.html`'s script and re-publish the widget on your site.

## 7. Update the knowledge base later

Whenever the source documents change:

1. Edit the `.docx` files in `knowledge_base_jhu/`.
2. Re-run `python ingest.py` from `backend/` — it fully rebuilds the
   `jhu_knowledge` collection, so stale/removed content never lingers.
3. Restart (or redeploy) the server so it picks up the refreshed
   `jhu_vectordb/` data.

No code changes are needed for routine content updates.

## Notes

- The chatbot **only** answers from retrieved document context — if the
  answer isn't in the knowledge base, it responds with a warm handoff
  and a discovery-call prompt instead of guessing.
- Every response includes `sources`: the document filenames the answer
  was grounded in. The widget shows these in a small collapsed
  "Sources" line; the backend also logs them server-side per query for
  debugging/QA.
- Conversation history (last 6 messages) is sent with every request so
  Gemini has short-term context, and is kept entirely in the browser —
  no server-side session storage.
- The bot will describe client-facing outcomes (e.g. "we automatically
  send your onboarding materials") but is explicitly instructed never
  to name internal tools, software, or vendors — even if they appear in
  the source documents — so internal-only operational details never
  leak to a website visitor.
- Before removing the "Sources" line from the widget for production,
  note it's currently intentional for QA/demo purposes — sources are
  always logged server-side regardless, so hiding it from visitors
  loses no debugging capability.
